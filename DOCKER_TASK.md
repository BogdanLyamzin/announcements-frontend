# Практична робота — Контейнеризація дошки оголошень

**Тривалість: 50 хвилин.**

Ви маєте готовий Next.js-фронтенд і власний REST API дошки оголошень. Підготуйте застосунок до запуску в Docker, починаючи з фронтенду.

**Основний результат заняття — самостійно написаний Dockerfile фронтенду, зібраний образ і запущений контейнер із доступним інтерфейсом. Якщо за заняття ви встигнете виконати лише першу частину, це завершений результат практики.**

Після першої частини переходьте до підготовки бекенду, а потім до Compose — у міру готовності та наявності часу. Усі конфігурації пишете самостійно; готові Dockerfile та Compose-файл не надаються.

Реалізація Socket.IO не є передумовою цієї практики. Для роботи з даними достатньо REST API та кнопки «Оновити список».

## Перед початком

- Docker встановлений і запущений; команди `docker version` і `docker compose version` працюють.
- У вас є вихідний код готового фронтенду з `package.json` і `package-lock.json`.
- У заготовці фронтенду вже є команди `build` та `start`. Перегляньте їх перед роботою.
- Порт `3001` вільний: локальний сервер розробки фронтенду потрібно зупинити.
- Для частин 2–3 потрібен власний робочий бекенд ДЗ із PostgreSQL, Prisma-схемою та наявними міграціями.

Команди компіляції та запуску зібраного бекенду можуть ще бути відсутні: у попередніх домашніх завданнях їх додавання не вимагалося. Ви налаштуєте їх у другій частині. Мати готову конфігурацію збірки бекенду до початку заняття не потрібно.

## Частина 1. Dockerfile для фронтенду — основне завдання

### 1. Перевірте команди запуску

Відкрийте `package.json` фронтенду та знайдіть команди `build` і `start`. Поясніть, яка команда збирає застосунок, а яка запускає вже зібраний результат.

Поточна команда `start` у заготовці містить `--hostname localhost`. Для контейнера потрібна адреса прослуховування `0.0.0.0` та порт `3001`. Самостійно додайте окрему команду запуску для контейнера, наприклад з назвою `start:docker`, зберігши локальні команди розробки.

### 2. Напишіть .dockerignore

Створіть `.dockerignore` у корені фронтенду. Виключіть із контексту складання:

- локальні `node_modules`;
- результати попередніх збірок `.next`;
- `.git`;
- локальні `.env`-файли із секретами;
- журнали та тимчасові файли компіляції.

Залежності й результат збірки повинні створюватися всередині образу. Файл `.env.example` можна залишити як приклад налаштувань без справжніх секретів.

### 3. Напишіть Dockerfile

Створіть Dockerfile поруч із `package.json`. Він має:

1. Використовувати сумісний із проєктом образ Node.js, наприклад Node.js 24.
2. Встановлювати робочу директорію всередині образу.
3. Копіювати `package.json` і `package-lock.json` та встановлювати залежності через `npm ci`.
4. Копіювати вихідний код із урахуванням `.dockerignore`.
5. Виконувати `npm run build` під час збірки образу.
6. Встановлювати режим роботи `NODE_ENV=production` для запуску застосунку.
7. Документувати порт `3001` через `EXPOSE`.
8. Запускати зібраний Next.js-застосунок через підготовлену команду для контейнера.

Запуск через `npm run dev` не підходить. Застосунок має слухати `0.0.0.0:3001`.

Для основної частини достатньо звичайного одноетапного Dockerfile та запуску через `next start`. Налаштовувати `output: "standalone"` не обов’язково.

### 4. Зберіть образ і запустіть контейнер

Із папки фронтенду зберіть образ:

```powershell
docker build -t announcements-frontend .
```

Потім запустіть контейнер:

```powershell
docker run --rm -p 3001:3001 announcements-frontend
```

Відкрийте `http://localhost:3001`. Переконайтеся, що інтерфейс завантажується та можна відкрити сторінки входу й реєстрації.

На цьому етапі перевіряється робота контейнера фронтенду. Якщо API ще не підключений, повідомлення про неможливість завантажити оголошення не означає, що контейнер фронтенду запущений неправильно.

Будьте готові пояснити різницю між `EXPOSE` у Dockerfile та публікацією порту через `-p`.

### 5. За можливості підключіть локальний API

Якщо бекенд уже працює на комп’ютері, у Docker Desktop можна передати його адресу контейнеру фронтенду:

```powershell
docker run --rm -p 3001:3001 -e BACKEND_URL=http://host.docker.internal:3000 announcements-frontend
```

Зупиніть попередній контейнер перед повторним запуском. Якщо REST API має префікс `/api`, додайте його до `BACKEND_URL`.

`host.docker.internal` у цьому прикладі — адреса комп’ютера з погляду контейнера Docker Desktop. На Linux Docker Engine налаштування доступу до хоста може відрізнятися.

Якщо API доступний, додатково перевірте вхід і CRUD через інтерфейс. Підключення API на цьому підетапі не є умовою виконання основного завдання.

## Частина 2. Підготовка бекенду та його Dockerfile

Переходьте до цієї частини після успішного запуску фронтенду в контейнері.

### 1. Налаштуйте збірку бекенду

Самостійно підготуйте:

- конфігурацію TypeScript для отримання JavaScript-файлів, наприклад `tsconfig.build.json`;
- npm-команду `build`, яка виконує компіляцію;
- npm-команду `start`, яка запускає фактично отриманий JavaScript-файл точки входу без режиму `watch`;
- команду генерації Prisma Client;
- команду застосування наявних міграцій, що відповідає встановленій версії Prisma.

Перевірте результат компіляції: шлях у команді `start` повинен відповідати реальному розташуванню зібраного файлу. Врахуйте структуру свого проєкту, розташування згенерованого Prisma Client та імпорти TypeScript.

Генерацію Prisma Client і застосування міграцій можна оформити npm-скриптами або запускати відповідними CLI-командами. Не вважайте, що ці скрипти вже є у вашому ДЗ.

### 2. Напишіть Dockerfile і .dockerignore

Dockerfile бекенду має:

1. Використовувати сумісний образ Node.js.
2. Встановлювати залежності з lock-файла.
3. Копіювати вихідний код, Prisma-схему та міграції.
4. Генерувати Prisma Client усередині образу перед компіляцією.
5. Збирати TypeScript і запускати отриманий JavaScript.
6. Забезпечувати доступність API на порту `3000` поза контейнером.

Додайте `.dockerignore` для локальних залежностей, результатів збірки, `.git` і файлів із секретами. Збірка образу не повинна вимагати доступної PostgreSQL. Міграції застосовуватимуться після готовності бази під час запуску стеку.

Якщо Socket.IO вже реалізований, він продовжує працювати через той самий HTTP-сервер. Додавати Socket.IO спеціально для цього завдання не потрібно.

## Частина 3. Compose для всього застосунку

Переходьте до цієї частини, коли Dockerfile фронтенду й бекенду вже готові. Розмістіть `compose.yaml` у спільній батьківській директорії та правильно вкажіть контексти збірки.

Опишіть три основні сервіси:

| Сервіс | Призначення |
| --- | --- |
| `frontend` | Next.js-фронтенд, порт `3001` |
| `backend` | REST API, порт `3000` |
| `db` | PostgreSQL, внутрішній порт `5432` |

Вимоги до стеку:

- PostgreSQL використовує офіційний образ із визначеною основною версією та іменований том для даних.
- Для БД налаштований `healthcheck`. Залежний запуск із міграціями очікує `service_healthy`.
- Наявні міграції застосовуються до готової бази перед прийманням API-запитів: командою запуску або окремим одноразовим сервісом. Потрібний інструмент міграцій доступний у відповідному образі.
- Бекенд отримує `DATABASE_URL`, JWT-секрет та інші налаштування через оточення.
- Фронтенд отримує адресу API через `BACKEND_URL`.
- Порти `3000` і `3001` опубліковані на комп’ютері; публікувати порт PostgreSQL не обов’язково.
- Створено `.env.example` без справжніх секретів, а локальний `.env` додано до `.gitignore`.

Для повного стеку використовуйте такі адреси:

| Хто звертається | Адреса або налаштування |
| --- | --- |
| Бекенд → PostgreSQL | Хост `db`, порт `5432` у `DATABASE_URL` |
| Сервер Next.js → API | `BACKEND_URL=http://backend:3000` |
| Браузер → фронтенд | `http://localhost:3001` |

За наявності REST-префікса `/api` додайте його до `BACKEND_URL`. `localhost` усередині контейнера вказує на цей контейнер; для звернення до іншого сервісу Compose використовуйте ім’я сервісу.

Файл `.env` поруч із Compose використовується для підстановки значень. Потрібні змінні для контейнерів передавайте через `environment` або `env_file`.

Зібраний стек має запускатися командою:

```powershell
docker compose up --build
```

## Змінні Next.js та необов’язкові можливості

`BACKEND_URL` використовується сервером Next.js і передається під час запуску контейнера. Змінні `NEXT_PUBLIC_*` вбудовуються в браузерний код під час `next build`. Якщо змінюєте їхні значення, передайте їх у процес збірки, наприклад через `ARG` у Dockerfile та `build.args` у Compose.

Для фотографій врахуйте `NEXT_PUBLIC_UPLOADS_ENABLED` і `NEXT_PUBLIC_UPLOAD_FIELD`. Для перевірки без Cloudinary можна використати `NEXT_PUBLIC_UPLOADS_ENABLED=false`, якщо ваш API приймає JSON. Якщо фото ввімкнені, налаштування Cloudinary передаються лише бекенду, а контейнер має дозволяти запис тимчасових файлів.

Якщо Socket.IO вже реалізований, додатково налаштуйте `NEXT_PUBLIC_SOCKET_URL=http://localhost:3000` під час збірки фронтенду та дозвольте origin `http://localhost:3001` у CORS сервера Socket.IO. Браузер не використовує внутрішнє ім’я сервісу `backend`.

## Що показати через демонстрацію екрана

### Після першої частини — основний результат

1. Покажіть написані вами Dockerfile, `.dockerignore` і команду запуску для контейнера.
2. Зберіть образ і запустіть контейнер фронтенду.
3. Відкрийте `http://localhost:3001` і покажіть доступний інтерфейс.
4. Поясніть порядок інструкцій Dockerfile, відмінність образу від контейнера та призначення публікації порту.

### Якщо виконали другу та третю частини

1. Запустіть стек через `docker compose up --build` і покажіть `docker compose ps`.
2. Зареєструйте користувача, створіть і змініть оголошення через фронтенд. Оновіть список кнопкою «Оновити список».
3. Виконайте `docker compose down`, потім знову запустіть стек через `docker compose up`.
4. Покажіть, що користувач і оголошення залишилися в базі, після чого перевірте видалення власного оголошення.

Для перевірки збереження даних не використовуйте `docker compose down -v`: цей параметр видаляє іменовані томи.

Якщо Socket.IO вже реалізований, окремо покажіть автоматичне оновлення списку в іншому вікні. Це додаткова перевірка.

## Критерії основного завдання

- [ ] Ви самостійно написали Dockerfile та `.dockerignore` фронтенду.
- [ ] Образ успішно збирається, залежності встановлюються всередині образу.
- [ ] Під час збірки виконується `npm run build`.
- [ ] Контейнер запускає зібраний застосунок без сервера розробки.
- [ ] Фронтенд слухає `0.0.0.0:3001` і доступний із браузера через опублікований порт.
- [ ] Локальні залежності, попередня збірка та файли із секретами не потрапляють у контекст складання.
- [ ] Ви можете пояснити інструкції власного Dockerfile.

Підготовка бекенду й Compose — наступні результати для тих, хто встиг виконати першу частину. Їх відсутність не скасовує виконання основного завдання.

## Орієнтир на 50 хвилин

| Час | Робота |
| --- | --- |
| 0–5 хв | Перевірити Docker та команди фронтенду |
| 5–12 хв | Написати .dockerignore і команду запуску для контейнера |
| 12–32 хв | Написати Dockerfile та зібрати образ фронтенду |
| 32–42 хв | Запустити контейнер, перевірити доступність, виправити помилки |
| 42–50 хв | Продемонструвати й пояснити результат |

Якщо завершили раніше, переходьте до другої частини, а потім до третьої. Не потрібно встигнути всі три частини за 50 хвилин.

## Додаткові покращення

Після робочого запуску можна обрати одне покращення:

- Налаштувати багатоетапну збірку та зменшити кінцевий образ.
- Перевести фронтенд на `output: "standalone"`, перенісши потрібні статичні файли.
- Запускати процеси застосунків від непривілейованого користувача.
- Додати перевірку готовності бекенду для повного Compose-стеку.

Публічний домен, HTTPS і розміщення на віддаленому сервері до цієї практики не входять.
