# Практична робота — Дошка оголошень у реальному часі

**Тривалість: 50 хвилин.**

У домашніх завданнях ви створили REST API дошки оголошень: користувачі можуть реєструватися, входити, публікувати, редагувати та видаляти власні оголошення. Переглядати оголошення можуть усі відвідувачі.

Тепер до API підключений готовий фронтенд. Відкрийте дошку у двох вкладках. Якщо в одній вкладці створити оголошення, в іншій воно з’явиться лише після ручного оновлення списку.

Ваше завдання — додати оновлення дошки в реальному часі через **Socket.IO**.

## Очікуваний результат

Коли один користувач створює, редагує або видаляє оголошення, усі відвідувачі з відкритою дошкою автоматично бачать актуальний список. Натискати «Оновити список» або перезавантажувати сторінку не потрібно.

Наприклад:

1. Олена відкрила загальний список оголошень.
2. Андрій у своєму браузері створив оголошення «Продам велосипед».
3. Оголошення автоматично з’явилося у списку Олени.
4. Андрій змінив ціну — Олена побачила нову ціну.
5. Андрій видалив оголошення — воно зникло зі списку Олени.

У цій практиці оновлюється саме **загальний список на головній сторінці**. Автоматичне оновлення відкритої сторінки окремого оголошення не входить до обов’язкової частини.

## Що ви отримуєте

- Власний робочий бекенд із попередніх домашніх завдань.
- Готовий Next.js-фронтенд у директорії `practice/announcements-frontend`.
- Інтерфейс реєстрації, входу, перегляду, створення, редагування та видалення оголошень.
- Пошук, сортування та пагінацію списку.
- Уже встановлений у фронтенді пакет `socket.io-client`.
- Хук `src/hooks/use-announcements.ts` із функцією `refreshAnnouncements()` та позначкою `TODO(practice)`.

У заготовці ще немає підключення до Socket.IO та обробників його подій.

## Перед початком

Запустіть свій API та підключіть до нього фронтенд за інструкцією в [README.md](README.md).

Перевірте, що через інтерфейс уже працюють вхід, завантаження списку та створення оголошення. Якщо ці дії не працюють, спочатку перевірте налаштування API.

За типової конфігурації:

| Застосунок | Адреса |
| --- | --- |
| Express API та Socket.IO | `http://localhost:3000` |
| Next.js-фронтенд | `http://localhost:3001` |

У `.env.local` фронтенду змінна `BACKEND_URL` містить базову адресу REST API, а `NEXT_PUBLIC_SOCKET_URL` — адресу сервера Socket.IO. Якщо REST-маршрути мають префікс `/api`, він додається лише до `BACKEND_URL`. За стандартного налаштування Socket.IO значення `NEXT_PUBLIC_SOCKET_URL` залишається адресою сервера без `/api`.

Після зміни змінних оточення перезапустіть фронтенд.

Для цієї практики достатньо текстових оголошень. Якщо завантаження фото ще не налаштоване, можна використати JSON-режим фронтенду: `NEXT_PUBLIC_UPLOADS_ENABLED=false`.

## Частина 1. Бекенд

### 1. Підключіть Socket.IO

Встановіть пакет `socket.io` у проєкті бекенду.

Створіть HTTP-сервер для вашого Express-застосунку та підключіть до нього Socket.IO. REST API і Socket.IO мають працювати через **один HTTP-сервер на одному порту**. Застосунок не повинен одночасно запускати окремі сервери через старий `app.listen()` і новий HTTP-сервер.

У налаштуваннях CORS саме сервера Socket.IO дозвольте підключення з адреси фронтенду — за замовчуванням `http://localhost:3001`.

Дозвольте отримувати події також неавторизованим відвідувачам: список оголошень у нашому API публічний. Для цього завдання достатньо загальної розсилки всім підключеним клієнтам; кімнати не потрібні.

### 2. Додайте події про зміни

Сервер має надсилати три події:

| Подія | Коли надсилається | Дані |
| --- | --- | --- |
| `announcement:created` | Після успішного створення оголошення | `{ "id": 123 }` |
| `announcement:updated` | Після успішного оновлення оголошення | `{ "id": 123 }` |
| `announcement:deleted` | Після успішного видалення оголошення | `{ "id": 123 }` |

Замість `123` передавайте ідентифікатор відповідного оголошення.

Надсилайте повідомлення всім підключеним клієнтам через загальну розсилку Socket.IO. Контролери мають використовувати той самий екземпляр Socket.IO, який підключений до HTTP-сервера.

**Важливо:** подія надсилається лише після успішної зміни даних у базі. При помилках валідації, відсутності авторизації, спробі змінити чуже оголошення або помилці бази подія не надсилається.

### 3. Збережіть наявну логіку REST API

Створення, редагування та видалення продовжують виконуватися через наявні HTTP-маршрути:

- `POST /announcements`;
- `PATCH /announcements/:id`;
- `DELETE /announcements/:id`.

Збережіть перевірку токена, валідацію та перевірку власника оголошення. Socket.IO лише повідомляє, що дані змінилися. Клієнт не повинен самостійно надсилати подію про успішну зміну іншим користувачам.

## Частина 2. Фронтенд

### 1. Підключіться до Socket.IO

У хуку `src/hooks/use-announcements.ts` знайдіть позначку `TODO(practice)`.

Додайте клієнтське підключення до адреси зі змінної `NEXT_PUBLIC_SOCKET_URL`. Socket.IO підключається **безпосередньо до Express-сервера**, а не до REST-адаптера Next.js `/api/backend`.

Підключення має працювати і для відвідувача, який не увійшов до облікового запису.

### 2. Обробіть три події

Підпишіться на `announcement:created`, `announcement:updated` та `announcement:deleted`.

Після отримання будь-якої з цих подій викликайте готову функцію `refreshAnnouncements()`. Вона повторно запитає список через REST API та оновить дані інтерфейсу.

Не потрібно вручну додавати, змінювати чи видаляти картки в масиві: правильний список поверне сервер. Отриманого ідентифікатора достатньо для повідомлення про зміну; завантажувати окреме оголошення за ним у цій практиці не потрібно.

Збережіть поточний пошуковий запит, порядок сортування та номер сторінки. Подія не повинна безумовно скидати користувача на першу сторінку. Якщо після видалення остання сторінка перестала існувати, готовий компонент дошки вже коригує її номер.

Нове оголошення має з’явитися лише тоді, коли воно відповідає поточному пошуку та потрапляє на відкриту сторінку з урахуванням сортування.

### 3. Подбайте про життєвий цикл підключення

Використайте `useEffect` для підключення та підписок.

- Не створюйте нове з’єднання під час кожного рендеру.
- При очищенні ефекту знімайте додані ним обробники та закривайте створене ним з’єднання.
- Після зміни пошуку, сортування чи сторінки обробники мають використовувати актуальну функцію оновлення списку.
- Повторний перехід на головну сторінку не повинен накопичувати підписки й спричиняти кілька однакових оновлень на одну подію.

Для автоматичного оновлення не використовуйте перезавантаження сторінки або періодичні запити за таймером.

## Перевірка через демонстрацію екрана

### Сценарій 1. Створення

1. Відкрийте головну сторінку у вкладці спостерігача. Очистіть пошук, оберіть «Спочатку нові» та першу сторінку.
2. В іншій вкладці увійдіть і створіть оголошення з унікальною назвою.
3. Покажіть, що воно автоматично з’явилося у вкладці спостерігача. Лічильник оголошень також має оновитися.

### Сценарій 2. Редагування та видалення

1. Змініть ціну створеного оголошення.
2. Покажіть нову ціну у вкладці спостерігача без ручного оновлення.
3. Видаліть оголошення та переконайтеся, що картка зникла, а загальна кількість зменшилася.

### Сценарій 3. Пошук

1. У вкладці спостерігача введіть пошуковий запит, наприклад «велосипед».
2. В іншій вкладці створіть оголошення, назва якого містить це слово.
3. Покажіть, що результати оновилися, а текст пошуку та сортування збереглися.
4. Змініть назву цього оголошення так, щоб воно більше не відповідало пошуку. Картка має зникнути з результатів.

### Сценарій 4. Гість і права доступу

1. Відкрийте дошку в приватному вікні або іншому браузері без входу. Звичайні вкладки одного браузера можуть використовувати спільний обліковий запис.
2. Покажіть, що гість також отримує оновлення після створення оголошення.
3. Через Swagger або REST Client спробуйте змінити чуже оголошення. Сервер має повернути `403`, а подія `announcement:updated` не повинна надсилатися.

Для останньої перевірки можна показати отримані події в консолі браузера або мережеві запити: невдала зміна не повинна спричинити повторне завантаження списку у спостерігача.

## Критерії виконання

- [ ] REST API та Socket.IO працюють на одному HTTP-сервері.
- [ ] Сервер надсилає всі три події після успішної зміни в БД.
- [ ] Невдала операція не породжує подію про зміну.
- [ ] Відкритий список автоматично оновлюється після створення, редагування та видалення оголошення.
- [ ] Пошук, сортування та пагінація продовжують працювати.
- [ ] Оновлення отримують також неавторизовані відвідувачі.
- [ ] Підписки очищуються, повторні переходи не накопичують обробники.
- [ ] Перевірки авторизації та власника в REST API збережені.

## Додатково, якщо залишився час

Оберіть одне покращення:

- Показуйте стан підключення: «Підключено» / «З’єднання втрачено».
- Після відновлення з’єднання автоматично завантажуйте актуальний список, щоб побачити зміни, які відбулися під час відключення.
- Об’єднуйте кілька подій, отриманих за короткий проміжок часу, в одне оновлення списку.

Додаткові покращення не замінюють обов’язкові вимоги.
